# FIDELITY.md — what is real, what is replaced, what is approximated

Everything below is auditable: `node build.mjs` bundles Dify's own source files straight from `dify-src/web` (tag 1.17.1, read-only; nothing is copied or edited) and writes `dist/manifest.json` with the sha256 of every file that ended up in the bundle. `FIDELITY.generated.md` (re-generate with `node scripts/fidelity-table.mjs`) lists every import that the bundler redirected, with `file:line`.

Legend: **[R]** real Dify code, unmodified · **[S]** environment shim (replaces a module/global, never edits Dify code) · **[P]** hand port of code that cannot run outside React/Python (approximation, line references given) · **[A]** modelling assumption.

## 1. What runs unmodified [R]

14 Dify files, 3,2xx lines (list + hashes in `FIDELITY.generated.md`):

| area | files |
|---|---|
| CRDT / sync core | `collaboration/core/collaboration-manager.ts` (2053 lines, the whole class), `crdt-provider.ts`, `event-emitter.ts`, `websocket-manager.ts` (the real `WebSocketClient` class and `emitWithAuthGuard`; only its `io()` import and `@/config` are shimmed), `crdt-runtime.ts` (bundled but replaced at runtime, see S-3) |
| node data update path | `hooks/use-collaborative-workflow.ts`, `hooks/use-node-data-update.ts` (`handleNodeDataUpdate` merging `{...currentNode.data, ...data}`), `nodes/_base/hooks/use-node-crud.ts`, `hooks/use-nodes-sync-draft.ts` (the 5 s debounce caller) |
| saving | `workflow-app/hooks/use-nodes-sync-draft.ts` (leader/`sync_request` routing, `performLocalSync` with hash, `draft_workflow_not_sync` → refresh, page-close keepalive), `hooks/use-serial-async-callback.ts`, `store/workflow/workflow-draft-slice.ts` (es-toolkit `debounce(…, 5000)`), `workflow-app/hooks/use-workflow-refresh-draft.ts`, `hooks/use-workflow-update.ts` |
| libraries | `loro-crdt@1.15.1` (exact pin from `pnpm-workspace.yaml:199`), `es-toolkit@1.52.0`, `immer@11.1.18` — real npm packages |

React hooks are run **as plain functions**: `react` is shimmed so `useCallback(fn)=fn`, `useMemo(f)=f()`, `useRef(x)={current:x}`, `useEffect(f)` runs `f` once. Each simulated tab instantiates every hook once (React keeps them stable across renders; nothing re-renders here). No line of the hooks is edited.

## 2. Environment shims [S] (every line of replacement)

### Globals (src/sim/core.ts `installGlobals`)
| global | replacement | why |
|---|---|---|
| `Date.now`, `performance.now` | virtual clock (`1.8e12 + ms`) | determinism |
| `setTimeout/clearTimeout/setInterval` | virtual scheduler, min 1 ms; each timer fires inside the AsyncLocalStorage context of the tab that created it | debounces, retries, 20 s sync timeout, 500 ms refresh |
| `requestAnimationFrame` | per-tab 60 Hz frame lattice with random phase; **paused while the tab is hidden** (Chrome behaviour; same emulation as `repro/lib/harness.py HIDDEN_INIT`); optional extra delay per frame (`rafDelayMs`, = harness `__rafDelay`) | the CRDT→canvas apply path of the manager is entirely rAF driven |
| `document.visibilityState/addEventListener`, `window` | per-tab object | visibility → `graph_view_state` / leader demotion |
| `Math.random`, `crypto.randomUUID/getRandomValues` | seeded streams | reproducibility (`connectionId`, `requestId`) |
| `console.warn/error` | captured per tab (counted, 50 kept) | |

Every Dify call that reaches a "singleton" (`webSocketClient`, `collaborationManager`) or a browser global resolves, through `AsyncLocalStorage`, to the **current tab**. A tab's events run inside `als.run(tab, …)`; promise continuations keep the context.

### Module shims (`shims/*.ts`; the import sites are in `FIDELITY.generated.md`)
* **S-1 `socket.io-client`** → `src/sim/fakesocket.ts`, behaviour of socket.io-client 4.8.3 as read from its semantics: emits while disconnected are buffered and flushed *before* the `connect` handlers run (`Socket.onconnect → emitBuffered → emitReserved('connect')`); plain acks pending at disconnect are dropped; `disconnect()` = no reconnect; auto-reconnect with `reconnectionDelay 1000 ms, factor 2, randomizationFactor 0.5, max 5000 ms`, handshake ≈ 1.5 RTT + 30 ms; `connect_error` on every failed attempt. Not byte-level engine.io: no polling transport (Dify forces `transports:['websocket']`), no ping frames (heartbeat is modelled as detection delays, see §4).
* **S-2 `loro-crdt`** → the real package, `nodejs` build of the same Rust core as the browser build (same version 1.15.1; wasm binaries differ only in wasm-bindgen glue/size: nodejs 3,182,022 B vs browser 3,181,260 B). Only change: `decodeImportBlobMeta` is memoized by content (pure function; the relay delivers identical bytes to every member).
* **S-3 CRDT runtime injection**: `manager.crdtRuntime = {CRDTProvider (real), LoroDoc, LoroList, LoroMap, UndoManager}` — the same injection Dify's own unit tests use (`core/__tests__/test-crdt-runtime.ts`). `LoroDoc` is a thin function around the real `new LoroDoc()` that calls `setPeerId(random 60-bit from the tab's seeded stream)` so that LWW tie-breaking (lamport, peer id) is random per document like in a browser (a fresh doc, hence a fresh peer id, on every reconnect, exactly as `initializeCrdt` does).
* **S-4 singletons**: `websocket-manager` and `collaboration-manager` imports made by Dify files are redirected to proxies for the current tab's *instances of the real classes*.
* **S-5 stores**: `workflow/store`, `hooks-store`, `reactflow` (`useStoreApi` → in-memory store with `getState().{getNodes,setNodes,getEdges,edges,setEdges,transform}`), features store, system features (`enable_collaboration_mode=true`), `useNodesReadOnly` (constant `false`), agent-v2 predicates (`false`), `BlockEnum`.
* **S-6 HTTP**: `service/workflow` (`syncWorkflowDraft`, `fetchWorkflowDraft`) and `service/fetch` (`postWithKeepalive`) → simulated console API. `keepalive` bodies **> 64 KiB are rejected** (Fetch spec keepalive quota; Dify swallows the rejection, `fetch.ts:258`), which is what makes page-close saves of large graphs fail (`repro` S6F).

## 4. Simulated backend (src/sim/server.ts) — port of

* `controllers/console/socketio/workflow.py` (events `user_connect`, `collaboration_event`, `graph_event`, `disconnect`),
* `services/workflow_collaboration_service.py` — **same method names and control flow**: `authorize_and_join_workflow_room`, `disconnect_session`, `relay_collaboration_event` (graph_view_state with sequence check + demotion, `sync_request` forwarded to the leader with `sio.call(timeout=15)`, hidden-leader replacement, `graph_resync_request`, broadcast), `relay_graph_event`, `get_or_set_leader`, `handle_leader_disconnect`, `broadcast_leader_change`, `broadcast_online_users`, `_ensure_leader`, `_select_graph_leader` (visible-first, preferred sid), `_demote_leader_if_hidden`, `is_session_active`,
* `repositories/workflow_collaboration_repository.py` → in-memory maps (hash insertion order = Redis listpack order for <128 entries),
* `services/workflow_service.py:sync_draft_workflow` + `DraftWorkflowApi.post`: `unique_hash` check (**the hash is the real one**: `sha256(json.dumps({"graph":…}, sort_keys=True)+"None")`, reproduced by `src/sim/pyjson.ts`, verified against Python), `graph_only` for `_is_collaborative`, 409 `draft_workflow_not_sync`, draft row serialised (one request at a time), processing time `25 ms + 0.08 ms/node`.

Deviations (all assumptions **[A]**): single websocket worker; Redis TTLs/heartbeat keys are not expired (the server_id is always local so `is_session_active` = "socket still connected on the server", identical for one worker); the `graph_view_state` Redis lock is not needed because handlers are atomic here (no yield between the Lua write and the demotion); handler cost 0.4 ms/event, zero server CPU/egress limits (the real worker would be bandwidth/CPU bound at 100 users — see §6); `max_http_buffer_size` 10 MiB enforced (oversize ⇒ connection closed); engine.io heartbeat: a blackholed link is detected by both ends at `45 s − φ`, φ∈U(0,25 s) (pingInterval 25 s + pingTimeout 20 s), FIN/RST on graceful close and crash is seen after one uplink latency.

## 5. Network model (src/sim/net.ts)
Per tab: independent up/down FIFO pipes (TCP ordering), latency + uniform jitter, loss modelled as TCP retransmission delay (RTO 200 ms doubling; ordering preserved), optional bandwidth, modes `up | down(refuse) | blackhole(drop)`; HTTP uses the same latency on a separate non-FIFO path (`httpOffline` flag = harness `set_offline`). Binary payloads are copied across the wire (sender→server) and shared read-only on fan-out.

## 6. Performance layers (do not change results; verified bit-for-bit)
Real `loro-crdt@1.15.1` is slow and **leaks wasm memory** on exactly the operations Dify performs on every edit: the provider exports the sender's whole history (`doc.export({mode:'update'})`, ≈250-330 KB for 500 nodes) on every local commit, and every receiver calls `doc.import()` on it. Measured on this host (scripts in `/tmp` leak tests, summarised in REPORT §3): 8-30 ms and +0.16…0.57 MB of wasm memory per call when nodes contain List containers (`variables`, `prompt_template`); a 100-tab storm would need > 80 GB. (This is also a plausible explanation for the ≈1.2 GB per real tab seen in `memprobe`.) Therefore:
1. **diagnostics stubs** — the manager's log-only methods `startImportLog/finalizeImportLog/recordGraphSyncDiagnostic/captureSetNodesAnomaly` (collaboration-manager.ts:1583-1743, 1614-1660) are no-ops (they only append to bounded arrays nothing reads on the data path);
2. **`exportNode` / `getEdges` memo** invalidated by Loro events (by event path) and by every local write (`paranoid` mode re-computes every hit and throws on mismatch);
3. **lazy ingest** (`src/sim/tab.ts`): plain CRDT `update` deliveries and the rAF callbacks they cause are deferred until the next event that can observe the tab, then replayed in virtual-time order with the same frame lattice; an import is skipped only if a later blob covers its version vector **and** reaches the tab before the frame that would have run the callbacks registered by the skipped import (exact pruning rule, see comment in code);
4. **delta wire** (`src/sim/delta.ts`): in fast mode `export({mode:'update'})` returns a 16-byte marker bound to (sender doc, version) and `import(marker)` is `importJsonUpdates(changes the receiver lacks, up to that version)` taken from the sender's still-alive doc. Importing a blob is a set-union of changes, so state, version vector and `by:'import'` events are identical (`scripts/delta-equiv.mjs`: 5,719 random concurrent imports with nested maps+lists and out-of-order delivery, 0 mismatches). Bytes on the wire are accounted from an estimate of the real blob size (one real export per 4,000 ops + 1.5 B/op). Snapshots (joins, `sync_request` payloads) always use real bytes.

**Equivalence test** (`SIM_FAST=off|on|paranoid`, `src/cli.ts digests`): the whole S-series (37 scenarios) + 88 catalog cases, K=8 seeds, compared on {metrics, normalized draft digest, every save timestamp+author+status, per-client divergence}: exact mode (real blobs, no stubs/memo/lazy/delta) vs fast mode — **976/976 runs identical**. (An earlier pruning rule that ignored the frame constraint failed this test on 2/1,464 runs; the test is what exposed it.) Storm-level (N=6…8, three mixes, several seeds) comparisons are in REPORT §3. `SIM_FAST=off` runs everything exact.

**What is NOT modelled — and why it matters at 100 users**: client CPU. A real tab spends roughly the host time we measure per received update (blob decode+import 8-30 ms, then up to three 500-node exports, `cloneDeep` of 500 nodes and `isEqual` of 500 nodes per rAF cycle). At 67 updates/s (100 users x 0.67 edits/s) that is more than 100 % of a core, so real tabs fall behind; this simulator has infinite client CPU and therefore **under-estimates staleness windows and loss at N >= 50**. `rafDelayMs` is the stress knob (S1NR). Server CPU/egress is also unbounded (fan-out at 100 users is ≈ 67 x 99 x 250 KB ≈ 1.6 GB/s).
