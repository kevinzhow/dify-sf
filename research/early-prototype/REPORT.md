# 协作协议原型验证报告

目标：为 Dify 兼容工作流编辑器验证一套协作协议，核心承诺是三条：服务端已确认（ack）的编辑永不丢失；过期客户端不能覆盖更新的数据；所有客户端最终收敛。

结论：在 20,000 次随机运行（外加 200,000 次的加压运行）和 24 个命名场景里，I1–I5 五条不变量全部成立，违例数为 0。开发期间 fuzz 抓到过一个真实的设计漏洞（见第 6 节），已修复。故意注入 5 种缺陷后，检查器都能报出违例，说明零违例不是检查器失灵造成的。

工具链：docker 镜像 `swift:6.4`（Swift 6.4.1，tag 存在），Swift 6 语言模式，纯 Swift 无第三方依赖。

## 2. 设计摘要

**文档**：`Document` 含 nodes（id、type、title、位置、嵌套 `config`）和 edges（id、source/target 及 handle）。变量引用是 config 里的 `Value.ref(nodeId, output)`。删除节点后写入的 `Value.brokenRef` 是显式的"已断开"标记，只有服务端能写。节点和边的 id 由客户端生成，永不复用，删除后留墓碑。

**操作（Op）**：`addNode`、`removeNode`、`moveNode`、`setField(node, title | config路径, value)`、`addEdge`、`removeEdge`。客户端不会上传整图。

**服务端（sequencer）**：
- 每个 op 带 `(clientId, cseq, base)`。`cseq` 是幂等键，`base` 是客户端编辑时已应用的服务端版本。
- 服务端按 cseq 严格顺序处理每个客户端的 op，逐个校验，通过后分配全局 seq。
- 提交顺序是：先追加到持久日志，再改内存状态，最后广播。所以收到 ack 就意味着已经落盘。崩溃只会丢内存状态（会话、被拒绝的原因），不丢任何已提交的 op。
- 持久层 `Disk = snapshot + tail + archive`。每 N 条 op 做一次快照，快照里带去重索引（`client → cseq → seq`）；旧日志进 archive，只用于审计，恢复时不读。
- 恢复 = 快照 + 回放 tail。

**客户端状态机**（纯函数式，时间由外部传入）：
- `confirmed` 镜像服务端在 `lastSeq` 的状态；`outbox` 是待确认队列；`view = confirmed + outbox 里仍然有效的 op`。每次收到服务端消息都重新推导 view，这就是 rebase。
- 本地编辑立即乐观应用到 view，同时入队并发送。
- 重连、收到 `resyncRequired`、检测到序号空洞，都会发 `hello`；服务端回 `welcome`（日志增量，落后太多时给快照）。
- 断线重发未确认 op，靠 `(client, cseq)` 幂等。服务端对重复提交回 ack 或原拒绝原因，绝不重复应用。
- 每个 op 恰好上报一次终态（committed / rejected / lost），按 cseq 顺序释放。
- 客户端有两种模式：
  - `journaled`（写前日志）：outbox 持久化，崩溃或重载后原样恢复并重发。
  - `volatile`（不持久化）：只持久化两个计数器（`nextCseq`、`unresolvedFrom`）。崩溃后能确切知道哪些 cseq 在途，重连后向服务端查询：已提交的上报 committed，其余上报 `lost`。
- 服务端崩溃等同于所有会话重置。没有会话时收到 submit，服务端回 `resyncRequired`。

## 3. 冲突规则及理由

### 3.1 同字段写：基于过期版本的写入被拒绝，并通知

选择 **拒绝 + 通知**，不选"应用并通知被覆盖方"。

规则：字段寄存器是 `title`、`position`、每条 config 路径。路径前缀重叠视为同一字段（`model` 与 `model.name` 冲突，`model.name` 与 `model.temp` 不冲突）。如果另一个客户端在 `op.base` 之后写过重叠字段，该 op 被拒绝，返回 `conflict(哪个字段, 哪个 seq, 谁写的)`。同一客户端自己的写不算冲突，原因见第 7 节。

理由：
1. 用户痛点是"静默丢失"。拒绝让更新的数据永远不被过期客户端覆盖，I2 因此成为协议的结构性保证，不依赖用户或 UI 的行为。
2. "应用并通知被覆盖方"意味着被覆盖方的数据已经丢了，只能事后补救。
3. 被拒绝方不会丢意图。拒绝事件携带完整的 op，UI 可以提供"在最新版本上重新应用我的修改"：基于最新版本重发，必然通过。fuzz 里模拟了这个用户行为（`user.reapplied` 约 6 万次）。
4. 客户端早预警：收到会使本地待确认 op 必然失败的远端 op 时，客户端立刻把该 op 从 view 中隐藏，让用户看到真实的新值，并发出 `conflictDetected`。这样用户不会在过期值之上继续叠加编辑。服务端随后确认拒绝，才发终态事件。

代价：会增加用户看到"冲突"提示的次数，拖动节点位置这类高频操作也套用同一规则（`position` 是寄存器之一），体验上可能偏严格。可以按字段类型配置成"位置用 LWW 直接应用"，但那样要把 I2 对 position 的约束放宽。

长文本字段（prompt、code）：原型里按整字段 LWW + 同一套过期保护处理，会有冲突提示，未来可换 text CRDT/OT（见第 8 节）。列表按原子叶子处理，不提供按下标的编辑。

### 3.2 删除与编辑

- 编辑已删除的节点：拒绝，返回 `nodeDeleted`。
- 删除节点时，如果别人在 `base` 之后改过这个节点（任意字段、位置、连边），删除被拒绝，返回 `conflict`。理由是删除会销毁别人没被看到的工作。用户看到最新状态后再删就会成功（S7）。
- 删除一个被引用的节点：允许。引用它的字段在同一个 op 里被确定性地改成 `brokenRef`（显式标记），相连的边被删除。这个级联在服务端和所有客户端用同一份 `apply` 代码执行。
- 级联改写的字段也算"写"：如果有人在删除者的 `base` 之后写过引用字段，删除被拒绝。这是 fuzz 抓到的（第 6 节）。
- 新写入一个指向已删除节点的引用：拒绝，返回 `danglingReference`。客户端不能写 `brokenRef`。
- 因此任何时刻都不会出现没有标记的悬空引用（I4）。
- 删除一个已被别人删除的节点，返回 `nodeDeleted`，用户看到明确通知。
- 墓碑永久保留（id 不复用），所以"编辑已删节点"永远能被识别。

## 4. 不变量与检查方式

| 编号 | 内容 | 如何检查 |
|---|---|---|
| I1 | 所有已 ack 的 op 都在最终服务端状态里体现（除非被后续已 ack 的同字段 op 取代） | (a) 任何客户端被告知 committed 的 op，必须在持久日志的同一 seq 上且内容一致；(b) 最终服务端状态必须等于"独立 oracle"对日志的回放。oracle 用扁平的路径键值模型重写，与 `Document` 不共享代码。每次崩溃恢复后，还要比较恢复前后的状态 |
| I2 | 基于过期版本的写入不会静默覆盖更新的数据 | 对日志里每个写 W，检查 `(W.base, W.seq)` 之间没有其他客户端写过它的目标寄存器；删除的目标包括被级联改写的字段。这是严格检查，不使用"同客户端豁免"这个捷径 |
| I3 | 静默后所有客户端的文档等于服务端 | 逐客户端比较 `confirmed == server.doc` 且 `view == server.doc`（含版本戳和墓碑） |
| I4 | 没有无标记的悬空引用 | 服务端文档和所有客户端 view 每 10 步检查一次，结束时再查一次 |
| I5 | 每个客户端 op 恰好以一个明确终态结束，且终态如实 | 每个 op 恰好一个终态；committed 必须在日志里；rejected 或 lost 必须不在日志里；日志里的每个 op 的客户端都知道已保存 |

另外有日志卫生检查：seq 连续，每个客户端的 cseq 严格递增（防重复提交）。

静默（quiescence）的流程：停止编辑和故障注入，恢复所有链路、客户端和服务端，一直运行到所有客户端收敛。

## 5. 结果

### 5.1 命名场景（`collab-sim --scenarios-only`，24 个，全部通过）

| 场景 | 变体 | 观察到的行为 |
|---|---|---|
| S1 两人改不同节点 | 不同节点；同节点不同字段 | 全部提交，0 拒绝，收敛 |
| S2 两人改同一节点同一字段 | A 先 / B 先 / 路径重叠 / 拒绝后重新应用 | 先排序者保留；后者收到 `conflict`，其屏幕显示获胜值；重新应用后成功。`model` 与 `model.name` 冲突，`model.name` 与 `model.temp` 合并 |
| S3 过期标签页回来 | 日志追赶 / 快照加入 | 过期的 prompt、move、delete 被拒绝并通知；对未改动节点的编辑正常生效；没有覆盖 |
| S4 断网重连 | 链路在 submit 前断开；服务端已提交但 ack 丢失；40% 丢包 + 20% 重复 + 链路抖动 | 离线编辑重连后全部送达；重发不重复提交（日志只有 1 条）；客户端重连后得知已保存 |
| S5 客户端崩溃 | journaled / volatile / 服务端已提交但 ack 未到 | journaled：重启后全部提交。volatile：明确上报 `lost`，且不在日志里；"服务端已提交但客户端没收到 ack"的 op 被正确识别为已保存 |
| S6 快速编辑后立即关闭或重载 | journaled / volatile | journaled：0 丢失，最后的草稿保留。volatile：已保存的 op 是前缀（无空洞），其余明确上报 lost |
| S7 删除 vs 编辑 / 引用 | 先编辑后过期删除；先删除后编辑；删被引用节点；引用并发被删节点；双删；连到已删节点的边 | 过期删除被拒绝，编辑得以保留；对已删节点的编辑收到 `nodeDeleted`；引用变成 `brokenRef` 且边一并删除；新引用已删节点收到 `danglingReference` |
| S8（附加）服务端崩溃 | 重启后保留已 ack 的 op；日志已写入但广播丢失 | 恢复后状态相等；客户端重连后得知已保存 |

### 5.4 Dart 客户端移植（可选项）

`dart/lib/model.dart`（文档、校验、应用）和 `dart/lib/client.dart`（状态机）是 Swift 实现的直译。4 个测试覆盖：S2 冲突 + 早预警 + 重新应用、不同字段不冲突、S7 引用断开、乱序广播缓冲 + journal 恢复 + volatile 上报 lost。`dart test` 通过，`dart analyze` 无问题。这说明 Flutter 侧做法直接：状态机是纯数据 + 一组消息，没有任何平台相关的东西。没有做 Swift 与 Dart 的跨语言黄金对拍，那是正式版本该补的。

## 6. 开发中发现的问题及修复

1. **删除的级联改写绕过了过期保护（fuzz 发现，I2）**。最初删除节点只检查被删节点本身有没有被别人动过。fuzz 在前 2,000 个种子里有 28 次违例（1.4%），例子：c1 刚写了 `n4.inputs = ref(n0)`，c0（没看到这个写）删除 n0。级联把 c1 的字段改成了 `brokenRef`，并把字段版本戳记成 c0 的。随后 c0 又覆盖了这个字段，而这个字段背后的 c1 的写入 c0 根本没见过。修复：删除节点前，对所有会被级联改写的引用字段也做过期检查，有别人在 `base` 之后写过就拒绝删除（`Document.validate` 的 `removeNode` 分支）。同时把 I2 检查器的目标集扩展为"该 op 实际改写的全部寄存器"。修复后 200,000 次运行零违例。

2. **客户端的一个误报检查**。我在客户端 welcome 处理里加过"服务端 head 落后于客户端 seq 就报违规"。fuzz 里 welcome 被乱序延迟后，head 比客户端当前 seq 小很正常，不是缺陷。去掉了，"服务端回退"改由 I1 的日志对比来抓（先 ack 后落盘变异就是靠它抓到的）。

以下是设计阶段就预见并实现的几点，没有被 fuzz 反推出来，列在这里是因为它们是协议能成立的必要条件：被拒绝的 op 也必须推进服务端的 cseq（否则后续 op 被当成空洞卡死）；volatile 客户端崩溃后用 `willResendFrom` 声明放弃的 cseq；终态按 cseq 顺序释放以保持持久化指针连续；客户端首次加入用 `lastSeq = nil` 请求快照（否则拿不到初始图）；服务端按 session 门控，没有 hello 的 submit 一律回 `resyncRequired`。这些行为现在都由 fuzz 和场景持续验证，但如果有人改动其中任一项，应当是 fuzz 失败而不是线上才发现。

## 7. 关键推理：同客户端豁免为什么成立

服务端只记每个字段的最后一次写入（序号、客户端）。如果最后一次写入来自同一客户端，则不报冲突。这个捷径成立的原因：同一客户端的 op 按 cseq 顺序处理，且 base 单调不减。如果最后一次是我写的，那它通过检查时说明 `(它的base, 它的seq)` 之间没有别人写过；而我之后的 op base 不会比它更小，所以我之后的 op 看到的窗口是它的子集。这个证明不依赖 fuzz，但 I2 检查器是严格版本（不使用这个捷径），所以任何破坏它的实现缺陷都会被报出来。第 6 节的级联漏洞就是这个捷径被"级联写入记在删除者名下"绕开了。

## 8. 已知限制

- **没有真实网络和真实持久化**：网络是模拟的（延迟、乱序、丢包、重复、断线）；磁盘是内存里的结构，"崩溃只丢未落盘的"是按设计假设建模的，没有 fsync 语义、部分写入或磁盘损坏。
- **文本字段**：prompt、code 是整字段 LWW + 过期保护，两个人同时改同一个 prompt 的不同段落会冲突，后者被拒绝。要做到合并需要 text CRDT/OT，这是后续工作。列表也是原子值，没有按下标编辑；建议数组类配置在真实产品里改成"id → 项目"的 map。
- **删除更严格带来的代价**：被频繁编辑的节点，过期客户端想删它会被拒绝，需要刷新后再删一次。这是有意的取舍（保护别人的工作），但需要产品层面确认。
- **去重索引和墓碑只增不减**：快照里的 `client → cseq → seq` 索引，以及墓碑，都没有回收机制。真实系统需要会话过期（超过期限的客户端必须以"有未保存修改，请人工处理"重新加入），并定期回收。
- **客户端 `volatile` 模式会丢失未发送的编辑**：协议保证"明确告知丢了哪些 cseq"，但内容找不回来。产品应当使用 journaled（写前日志，如 IndexedDB），volatile 只作为兜底。
- **没有覆盖的内容**：认证和权限、多文档、撤销/重做、Dify DSL 的完整字段（只建模了 id/type/title/位置/嵌套 config/边/引用）、引用的输出名是否存在、节点环检测、本地存储自身被清空的情况。
- **模型假设**：每个客户端的 cseq 严格单调；node/edge id 全局唯一（生产里用 UUID）；服务端是单写者（没有多副本）。
- fuzz 的"用户"是随机的，不是真实编辑行为；拒绝比例（约 12% 的 op，其中冲突约 8%）大概高于真实使用，目的是压测，不是估计线上冲突率。

## 9. 与 Dify 复现结果对照的提示

同一份 S1–S7：本协议下

| 场景 | 本协议的结果 |
|---|---|
| S1 | 两边都保留 |
| S2 | 先到者生效，后到者被明确拒绝并看到新值，不会静默覆盖 |
| S3 | 过期客户端的冲突部分被拒绝并通知，不冲突部分生效 |
| S4 | 断线期间的编辑重连后补发，不丢不重 |
| S5 | journaled 客户端无损；volatile 客户端明确知道丢了什么 |
| S6 | 同 S5 |
| S7 | 删除与编辑冲突都有显式通知；引用显式断开，没有悬空 |

## 10. 重跑命令

所有命令在 `research/proto` 下执行；`run-swift.sh` 等价于：

```
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -e SWIFT_DETERMINISTIC_HASHING=1 \
  -v "$PWD":/work -w /work swift:6.4 swift <args>
```

./run-swift.sh test                                       # 全部测试（debug，约 3.5 分钟，含 10,000 次 fuzz）
./run-swift.sh test -c release -Xswiftc -enable-testing   # 同样的测试，release，约 30 秒
