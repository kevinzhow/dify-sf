# 协作冲突用例目录（初稿 v0.1，2026-10-16）

目的：穷举可复现的协作冲突情况。每个用例同时在 Dify 和 dify-sf 上执行，量化"丢没丢、覆盖没覆盖、一不一致"，形成对比计分表，并作为 dify-sf 的永久回归测试。

## 1. 指标（每次运行都判，结果只有 0/1）

| 编号 | 指标 | 判定 |
|---|---|---|
| M1 | 确认后丢失 | 用户的编辑已被确认（dify-sf：服务器回了 ack；Dify：界面已显示且无报错、等过自动保存），最终存储里却没有，也没有被后来的同字段写入合法取代 |
| M2 | 旧数据静默覆盖 | 基于旧版本的写入覆盖了更新的值，且被覆盖的一方没有收到任何提示 |
| M3 | 最终不一致 | 静默后，各客户端看到的图与服务器存储不相同 |
| M4 | 引用悬空 | 有字段引用了已不存在的节点或输出，且没有显式的"已断开"标记 |
| M5 | 编辑被吞 | 用户做了编辑，最终既没生效、也没有任何"未保存/被拒绝"的提示 |

每个用例跑 K 次（默认 20 次；时机类用例加网络抖动）。每个指标报"出现次数 / 有效次数"。执行器自身出错的记为 HARNESS_ERROR，不计入有效次数。

dify-sf 的验收线：所有用例 M1–M5 全为 0。

## 2. 维度

### 2.1 操作（8 种）
`addNode` 加节点 · `removeNode` 删节点 · `moveNode` 拖动 · `setField` 改配置字段 · `setTitle` 改标题 · `addEdge` 连线 · `removeEdge` 断线 · `setRef` 改引用（某字段引用另一节点的输出）

另有列表类字段的两种子操作：`listInsert`（加一项，如加输出变量、加提示词消息）和 `listRemove`（删一项）。Dify 在这里问题最集中。

### 2.2 目标关系（7 种）
| 编号 | 关系 | 例子 |
|---|---|---|
| R1 | 同一字段 | 都改节点 N 的 title |
| R2 | 同节点不同字段 | A 改 title，B 改 model |
| R3 | 路径重叠 | A 改 model，B 改 model.temperature |
| R4 | 同一列表的不同项 | A、B 各给代码节点加一个输出变量 |
| R5 | 不同节点 | A 改 N1，B 改 N2 |
| R6 | 引用关系 | A 删 N2，B 让 N1 引用 N2 的输出 |
| R7 | 结构关系 | 连线端点、容器（迭代/循环）里的子节点 |

### 2.3 时机（4 种）
| 编号 | 时机 |
|---|---|
| T1 | 并发：两次编辑间隔 < 200ms（落在 Dify 的防抖窗口内） |
| T2 | 先后但基于旧版本：B 的面板在 A 改之前就打开了，A 改完后 B 才提交 |
| T3 | 离线回来：B 断网期间编辑，A 在此期间也编辑，B 再联网 |
| T4 | 旧标签页：B 的标签页在后台放了很久（Dify 会触发 leader 改选），再回来编辑 |

### 2.4 故障（6 种）
| 编号 | 故障 |
|---|---|
| F0 | 无 |
| F1 | 网络抖动：单向 400ms 延迟、5% 丢包 |
| F2 | 编辑过程中断线再重连 |
| F3 | 编辑后 100ms 内关闭标签页或崩溃（保存前） |
| F4 | 负责保存的一方消失：Dify 的 leader 标签页关闭；dify-sf 的服务器 kill -9 后重启 |
| F5 | 重复提交（同一请求发两次） |

### 2.5 人数
2 人（默认）；3 人（只用于 R1/R4/R6 的子集）。

## 3. 组合规则（从全组合裁剪到可执行的规模）

全组合太大（操作对 × 关系 × 时机 × 故障 × 人数 ≈ 数万），按三层裁剪：

| 层 | 内容 | 规模估计 |
|---|---|---|
| A 核心 | 所有"操作对 × 适用关系"的合法组合，时机 T1、T2，故障 F0 | ≈ 90 |
| B 时机 | A 层每个用例再加 T3、T4 | ≈ 180 |
| C 故障 | 每个"操作对类别"选 1 个代表用例，乘 F1–F5 | ≈ 60 |
| D 单人基线 | 单人快速编辑后立即关闭/刷新/断网，覆盖 8 种操作 | ≈ 24 |
| E 三人 | R1/R4/R6 的代表用例，3 人并发 | ≈ 12 |

合计约 360 个用例。每个用例有稳定编号，形如 `A-setField-R2-T1-F0-2p`。

"合法组合"由一张适用表决定，例如 `moveNode` 只有 R1/R5 有意义，`setRef` 必须配 R6，`listInsert` 配 R4。

## 4. 每个用例的预期结果（dify-sf 的语义）

| 情况 | 预期 |
|---|---|
| 不同节点、同节点不同字段、同列表不同项、不重叠路径 | 两边的修改都保留 |
| 同一内容字段（含路径重叠）、基于旧版本 | 先到的生效；后到的被拒绝，并收到"冲突：谁在什么时候改了这里"的提示，可一键在最新版本上重做 |
| 拖动/布局 | 后写赢，不提示（已定） |
| 删节点 vs 改该节点 | 先到的生效；后到的被拒绝并提示 |
| 删被引用的节点 | 允许；引用处变成显式的"已断开"标记，连线一并删除 |
| 离线/崩溃 | 已确认的永不丢；未确认的在恢复后重发（写前日志模式），或明确告诉用户"这几条没存上" |

每个用例文件里写明具体的预期终态，执行器用它判 M1–M5。

## 5. 用例文件格式

```yaml
id: A-listInsert-R4-T1-F0-2p
title: 两人同时给同一代码节点各加一个输出变量
graph: fixtures/code-node-basic.yml      # 初始图（Dify DSL）
users: [A, B]
steps:
  - { at: 0,   user: A, op: listInsert, node: code1, path: outputs, value: { name: a_out, type: string } }
  - { at: 50,  user: B, op: listInsert, node: code1, path: outputs, value: { name: b_out, type: string } }
faults: []
settle: 5s
expect:
  final:
    - { node: code1, path: outputs, contains: [a_out, b_out] }
  notices: []                              # dify-sf 不应产生冲突提示
repeat: 20
```

同一份文件，两个执行器：
- **Dify 执行器**：Playwright 驱动真实 Dify 页面完成每一步，等自动保存后从接口读回草稿判分；故障用浏览器的离线、限速，以及关闭标签页来注入。
- **dify-sf 执行器**：两种模式。确定性模拟器（秒级，可跑上万次）；真实服务器 + 真实客户端进程（故障用 kill -9 和 TCP 代理注入）。

## 6. 计分表

每个用例一行：用例编号、说明、Dify 的 M1–M5（次数/有效次数）、dify-sf 的 M1–M5。另附汇总：按维度统计 Dify 出问题的比例。整套用例进 dify-sf 的 CI，任何改动都要保持全 0；以后发现新情况，先加用例再修。
