# Research: how Dify 1.17.1 loses collaborative edits, and how it was measured

This directory holds the methods and raw results behind `docs/results/dify-vs-difysf.md`. Everything here measures
**Dify**; dify-sf's own tests are described in `docs/testing.md`. Paths in the reports are relative to the repository
root (`research/...`); run the scripts from there unless a README says otherwise.

| directory | method | main result |
|---|---|---|
| `real-browser/` | Real Dify 1.17.1 (docker compose) driven by Playwright with real Chromium tabs; scripted scenarios S1-S10, 20 runs each, a recording proxy for the collaboration websocket | `REPORT.md`, raw runs in `logs/*.jsonl` |
| `dify-sim/` | Code-level simulator: Dify's own collaboration and save code (collaboration manager, panel write-back, Loro WASM, relay, draft API) bundled unchanged and run under a virtual clock; calibrated against the real-browser runs | `REPORT.md`, `FIDELITY.md`, `CATALOG-RESULTS*.md`, `out/` |
| `formal/` | TLA+ models of Dify's and dify-sf's collaboration (properties P1-P5, exhaustive model checking of small configurations, counterexamples replayed on real Loro) and the closed-form loss formula with its Monte Carlo | `REPORT.md`, `analytic/NOTES.md`, `results/` |
| `catalog/` | The conflict catalog definition (metrics M1-M5, dimensions, tiers); tier A is generated by `dify-sim/src/catalog/cases.ts` and exported to `bench/catalog/A-cases.json` | `CATALOG.md` |
| `early-prototype/` | The first op-log protocol prototype (Swift + Dart) and its randomized checker, before the real server existed | `REPORT.md` |
| `memprobe/` | Memory of real Chromium tabs editing a 500-node Dify workflow (why 100 real browsers do not fit one machine) | |

## Requirements

* **Dify source.** `dify-sim` bundles Dify's web code at build time from a separate checkout of Dify 1.17.1
  (`DIFY_WEB=<checkout>/web node build.mjs`); no Dify source is copied into this repository. Dify is Apache-2.0.
* **real-browser:** Python 3.12, `pip install playwright requests`, `playwright install chromium`, a local disposable
  Dify 1.17.1 from Dify's own docker compose, and the throwaway accounts in `lib/difyapi.py` created in it (passwords via
  `REPRO_PW_ALICE` / `REPRO_PW_BOB`).
* **dify-sim:** Node 22 (`npm ci`), then `npx tsx src/cli.ts ...`; `scripts/run_all.sh` regenerates the report.
* **formal:** Java 21 and `tools/tla2tools.jar` (download from the TLA+ releases); `run_tlc.sh` runs on `TLC_HOST` over
  ssh or locally with `TLC_LOCAL=1`. The analytic part needs Python with numpy, scipy, matplotlib, loro.

## What each layer established

1. **Real browser:** Dify keeps different nodes and different fields mostly apart, but loses edits deterministically when
   the saving tab (the leader) leaves or crashes while others are online, after a leader hand-off (stale version hash),
   after 8 s offline, on closing a large graph (64 KiB keepalive limit), after an external write or import, and whenever
   two people add items to the same list or write the same field (silently, without notice).
2. **Code-level simulator:** the same Dify code reproduces every deterministic loss 120/120; the timing-dependent
   scenarios agree with the real browser once driven by the real runs' timings (`scripts/s2o_joint.ts`,
   `scripts/s1n_repro_timing.ts`); one stress scenario (main thread slowed by a JS hack) still differs.
3. **Formal models:** Dify violates all five properties (confirmed edits not lost, no silent stale overwrite, eventual
   consistency, no dangling references, nothing swallowed silently), each with a shortest counterexample; dify-sf satisfies
   them in every configuration checked exhaustively.
4. **Formula vs simulator:** with the formula's workload (`src/storm.ts`, mix `formula`) and its own loss definition
   (provenance chain, `src/sim/ledger.ts`), all six simulated load points (10-50 users, 400 ms and 2 s) fall inside their
   95% intervals (`formal/analytic/compare_formula_grid.py`); a two-user sweep (`scripts/pair_window.ts`) confirms the loss
   window exactly. 100 users run ~124x slower than real time in the simulator and are given by the formula.
5. **Catalog:** 88 tier-A cases, Dify (calibrated simulator) 33 with a loss, dify-sf 0 (`docs/results/scorecard-A.md`).

## Known limits

Real-browser data covers two-person scenarios only. Closing a 30-node graph (S6G) lost 2/20 in the real browser and
0/120 in the simulator, unexplained. The simulator's main-thread latency comes from one calibration
session. The persistence lag measured at the end of load runs depends on the quiet period chosen (40 s). See the
reports for the details and the open discrepancies.
