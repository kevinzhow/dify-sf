# Model provider plugins and capabilities

Integrations displays a curated catalog of ten official model providers. The model forms come from their pinned definitions; settings and selected model parameter rules read the same original plugin schema used by workflow execution. This preserves provider-specific context limits, output limits, vision, tool features and parameters instead of substituting a generic 4K model.

Open **Integrations → Manage model plugins** to inspect the actual daemon installation state. Owners and administrators can install, update to the server's reviewed package version, or remove a plugin. Other workspace members can read status. The backend restricts package selection to official server pins, validates the package checksum and enables the daemon's signature verification. The pin is a reviewed version, rather than a claim that it is the marketplace's newest release. Arbitrary third-party packages, marketplace discovery and automatic updates are outside this manager.

Removing a plugin preserves saved provider/model credentials, selected credential IDs and workflow documents. Affected models remain visible with a missing-plugin indication; their configuration can be recovered after installation. Removal checks the current installation ID so an old confirmation cannot remove a different replacement installation.

## Configuring a custom endpoint

Use the provider whose plugin supports the endpoint and model name. The OpenAI plugin inherits metadata from a recognized base model; it cannot infer arbitrary aliases such as `codex/gpt-6.1-terra`. Use **OpenAI-compatible** for such aliases and a custom endpoint. Select its API type explicitly, including **Responses** where required. Enter context, maximum output, vision and tool settings according to that endpoint's actual capabilities; a name alone does not establish them.

The initial form includes its LLM-specific fields. Editing an existing custom model loads the same model/type context and preserves a pristine masked secret. Saving changed capabilities causes subsequent model lists, node selectors and parameter rules to read the updated original plugin schema. Switching provider types is an explicit user configuration change; installation does not move an existing model or copy its credentials into another provider.

## Failure states and API

A failed installation-list request is **unknown**, not an empty installed-plugin list. A failed model-schema read preserves the saved model row and any previously verified metadata, labels its availability as unknown, and avoids invented capabilities. An unrecognized model is unavailable with a stable error code. Raw daemon errors and tracebacks can contain configuration details and are not returned through these settings endpoints.

| Endpoint | Behavior |
|---|---|
| `GET /v1/workspace/model-provider-plugins` | Read the ten providers and actual installation states. |
| `POST /v1/workspace/model-provider-plugins/{org}/{plugin}/install` | Install or update to the server pin; owners/admins only. |
| `GET /v1/workspace/model-provider-plugins/tasks/{uuid}` | Read sanitized installation progress. |
| `POST /v1/workspace/model-provider-plugins/{org}/{plugin}/uninstall` | Remove the confirmed `installation_id`; owners/admins only. |

Model list entries add `schema_status` for unknown/unavailable metadata and `schema_error` for `plugin_not_installed`, `model_schema_missing` or `model_schema_unavailable`. Successful metadata keeps the existing response shape. Metadata requests share a bounded cache; independent models/providers resolve concurrently, preserving catalog and model order.

The runtime profile pins daemon 0.6.11, which includes the upstream [shared-runtime installation fix](https://github.com/langgenius/dify-plugin-daemon/pull/804). Its immediate removal/reinstall path was verified through the management API with the signed compatible plugin and a deterministic local Responses server. All ten signed packages and twelve schema cases were also exercised at the profile's 1024 MiB / 1 CPU limit. These local checks do not claim paid-provider validation or test a user's custom endpoint.

Form fixtures are generated by `tool/gen_model_provider_forms_fixture.py`; `--check` detects definition drift. `tool/check_provider_plugins.py` verifies that the bundled definitions, e2e package lock and server resource agree. Widget, transport, PostgreSQL route and schema tests cover conditional fields, secret preservation, permissions, installation state, failure visibility and recovery.
